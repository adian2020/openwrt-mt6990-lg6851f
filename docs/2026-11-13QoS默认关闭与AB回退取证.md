# QoS默认关闭与A/B回退取证

本次仅修复源码和编译测试，不启动云编译，自动监控保持关闭。软件源扩充与启动提速的未完成改动仍在其他工作目录，未合入本次修改。

## 证据与边界

用户提供Linux 6.18.44上的全局CPU stall：CPU2接收路径包含DPMAIF、CCCI、CCMNI、IP接收，CPU1栈涉及mt76发送、mirred、cake_enqueue及流哈希。停止自定义QoS并确认规则消失后，约15GB、最高500Mbps下载未重启。这是隔离QoS路径的重要对照，不能据此证明CAKE是唯一根因，也不能证明所有A/B回退均由同一故障造成。没有完整各CPU栈、锁状态及相同负载多轮对照，不能臆造内核死锁修复。

全库搜索定位如下（包含6.12的文件仅为同仓库旁证，目标构建使用6.18）：

- 自定义配置、控制脚本、init和首次配置规则均在target/linux/mediatek/mt6990/base-files。
- package/kernel/linux/modules/netsupport.mk保留sch_cake模块定义；.config保留kmod-sched-cake等手动启用依赖。模块存在/加载不等于挂载CAKE队列。
- target/linux/generic/backport-6.18/700-02至700-07包含CAKE配置拆分及cake_mq回移，701-01/02调整多队列同步及速率。
- target/linux/generic/hack-6.18/710-net-sched-sch_cake-configure-sync_time-via-debugfs.patch加入cake_mq同步时间debugfs接口。
- target/linux/generic/hack-6.18/712-net-sched-cake-autorate-ignore-idle-gaps.patch明确标注LG6851F维护者，改变autorate空闲窗口：大于250ms的空闲重置采样窗口，低于64KiB窗口不更新估计。它不直接改变流哈希或mirred锁；不能凭栈认定其无关或就是根因。
- package/network/utils/iproute2/patches/001-1-tc-cake-add-cake_mq-support.patch提供用户态多队列命令支持。当前脚本使用cake而非cake_mq。
- 厂商DPMAIF接收线程调用ccci_port_recv_skb，CCMNI包含netif_receive_skb/netif_rx分支；TC重定向增加IFB接收重入、分类、哈希及排队工作，可能改变负载和锁交互。未用停止CAKE后的稳定现象替代内核级证明。

以上内核/TC补丁本次均未改动，不读取debugfs时钟节点，不禁用MT6990-HANGDET或panic/watchdog，不删除依赖、不限制500Mbps。

## 已修复的可证明实现缺陷

1. 旧配置与控制脚本缺省值均为enabled=1，init以30秒/失败3秒循环持续调用start。现在新配置和缺省值为0；旧配置首次升级缺少safety_opt_in_version时，先停止并清理，再关闭并写版本1。后续用户明确启用的配置含版本1，后续迁移不再强行关闭。
2. 旧停止路径删除当前/历史WAN的整个root和clsact，即使没有本插件状态也可能影响其他队列或过滤器。现在只根据状态清理本插件WAN根句柄7ca0:及对应重定向，保留其他过滤器。仅在确由本插件创建、且双向均无过滤器时删除clsact。兼容旧单行状态的CAKE及pref10重定向清理。
3. 旧数字配置校验在stop之前，坏配置会阻止清理。现在stop及关闭状态先清理，随后才处理启用参数校验。
4. 旧配置过程没有互斥，且状态最后才写，失败可能留下IFB/CAKE而没有归属记录。现在所有操作由flock串行；先写状态、再配置，失败退出回滚。清理失败保留状态并返回错误，不假报成功。
5. 移除周期进程和respawn；procd仅管理启停及UCI重载，网络iface hotplug在ifup/ifupdate/ifdown处理规则。手动stop先写运行期停止标记，重载/重拨不清除该标记；只有明确start/restart才清除，配置enabled仍是最终开关。接口事件和关闭操作串行后重新读取配置。
6. 启用拒绝无归属的同名IFB、其他非默认根整形器以及已占用的过滤优先级，不覆盖其他插件的整形配置。重复接口事件在规则齐全时不重建；重拨换l3_device时清理旧设备并跟随新设备。

默认关闭且无状态时，不执行tc/ip/modprobe等配置命令。不强制把其他组件的根队列改成fq_codel；在用户描述的默认fq_codel环境中，本插件不替换它。手动开启仍使用CAKE、IFB、mirred、autorate-ingress、diffserv4、NAT及双向主机隔离。原max_hosts选项保留，但它原先也不是CAKE支持的强制客户端数量限制，不能把它宣传为36个硬件队列。

## 配置操作（仅供更新后用户手动选择）

默认无需操作，QoS保持关闭。若要测试启用：

```sh
uci set lg6851f_fair_qos.main.enabled='1'
uci commit lg6851f_fair_qos
/etc/init.d/lg6851f_fair_qos enable
/etc/init.d/lg6851f_fair_qos restart
```

持久关闭并清理：

```sh
uci set lg6851f_fair_qos.main.enabled='0'
uci commit lg6851f_fair_qos
/etc/init.d/lg6851f_fair_qos stop
```

单独service stop阻止本次启动中的自动事件恢复；若要跨重启关闭，应同时保存enabled=0。没有将本次隔离测试称为已实测启用后的高速稳定性。

## A/B回退如何取证

现有preinit的06_lg6851f_archive_pstore在进入服务前尝试保存ramoops；P46共享分区上的MT6990_CRASH_LOGS保存崩溃归档，MT6990_RUNTIME_LOGS/runtime.log及轮转文件保存启动后日志。它们在固件槽位之外，但原系统是否挂载/保留这些目录仍需实际检查。

新增scripts/lg6851f-collect-ab-failure.sh可在回退后尽早以root运行。它只读当前cmdline、slot_suffix线索、pstore、last_kmsg和已挂载P46目录，写一份临时报告；不自动挂载P46，不读取或写入misc，不标记启动成功，不切换槽位，不清空pstore，不重启。报告本身不包含所有历史归档正文，找到最新KERNEL_CRASH目录后需保留该目录的完整pstore及metadata/SHA256文件。

区分故障阶段：

- 有panic/Oops/HANGDET和完整调用栈：可定位已进入内核后的失败，结合启动ID、uptime及原失败槽位关联。
- 有VFS/rootfs挂载错误或服务早期失败：检查对应启动记录，不能先归咎于签名或QoS。
- 连内核日志也没有：可能是引导器校验、槽位重试状态、过早硬复位，或原系统已覆盖/清理记录；pstore为空不能证明没有故障。此时通常需要从上电开始的串口引导器日志。未核实厂商boot-control数据格式前不根据通用Android结构写misc或修改重试次数。

当前运行槽位仅说明回退后的状态，不证明哪个阶段失败。不要为了取证额外重启覆盖尚存的ramoops；本任务未操作实机或修改任何槽位保护及签名/Release打包代码。
