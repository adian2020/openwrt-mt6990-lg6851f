# 下载速度与 500 Mbps 历史运行状态对照

## 基线口径

用户提供的[成功记录](https://chatgpt.com/share/6aff1a0f-83b8-83e8-b6d4-fc43ab1b1d0e)不是“固件默认关闭 QoS 就能达到 500 Mbps”。实际是旧版固件默认开启 QoS，用户在 SSH 排查并操作后达到该速度。

2026-11-12 的原始用户输出显示：固件为 b6c3ce7f60950cddfa75be0d0c591ffc2ae4cc7a（v1.0.15），执行 `/etc/init.d/lg6851f_fair_qos stop` 后，ccmni2 为 fq_codel，ifb-cellular 不存在，入口重定向为空；随后用户报告下载约 15 GB，速率 300～500 Mbps，大部分时间接近 500 Mbps，没有重启，未计时。此为一次实际运行结果，不代表全部内核故障已解决。

分享记录中可核实的操作链以用户贴回的命令和结果为准，不把助手建议当作已执行操作，也不排除记录外还存在手动修改。不能只对比 enabled 默认值，还必须核对启动时是否曾安装过 CAKE/IFB、停止后的规则、实际中断/RPS 和配置状态。

当前设备实际固件为 11dd25e3839e5da76b9c38d7bc674020f3d435d9（v1.0.20），源码仓库后续的说明及临时测试工具提交不等于用户已刷入新固件。

## 本轮用户已验证的状态

- 旧版临时 QoS 开启约 100～150 Mbps；关闭后约 10～20 Mbps，均为下载 Mbps、同一测速节点。
- 关闭结果 OFF_RC=0；ccmni2 实际 fq_codel、IFB 和重定向已经清理，不能继续把这个状态归因于残留 CAKE。
- 不开启 CAKE/IFB，仅增加临时 nft 表 lg6851f_dscp_test，在蜂窝下载转发路径清除 IPv4/IPv6 非 CS0 的 DSCP 后，恢复约 150～250 Mbps。IPv4 计数命中，IPv6 当时没有命中。这是独立于完整 QoS 的部分恢复线索，不是最终 500 Mbps 修复或内核稳定性结论。
- 测速手机确认是 5a:b8:72:03:17:2a，5 GHz、80 MHz、HE 双流，收发 PHY 1200.9 Mbps。不能拿另一个 390 Mbps 单流客户端解释其速度上限；PHY 速率本身也不保证实际吞吐。
- OpenClash 配置为 0，用户确认未开启。150～250 Mbps 时十秒 CPU 平均约 46.7%，最忙核平均约 53.8%；没有证明持续单核满载，也不能排除短时突发。
- 原厂系统用户报告约 440～500 Mbps；250 Mbps 不作为完成目标。累计 Wi-Fi 失败计数不是当前丢包率，蜂窝 RX 降低也不能单独排除下游 TCP 反馈导致的降速。

## 下一步：一次被动运行状态采集

新增 `scripts/lg6851f-collect-download-state.sh`，由用户在现有互联网测速/下载期间运行，不恢复已经停止的局域网测试。默认两次计数采样间隔 10 秒，可选 0 或 20 秒。命令和无线站点查询也有耗时，分析应使用报告内 `/proc/uptime` 的实际间隔，而非假定严格十秒。

采集包括：实际固件身份、主要安装包版本、网络配置白名单、TC 与 DSCP 状态、标准 GRO/RPS/IRQ、脚本与 ROM 指纹、服务 PID/运行状态、CPU/softnet/接口与站点累计计数。仅在核实已挂载 P46 的分区身份后读取最多 8 份旧 upper 网络配置白名单，不主动挂载，不把归档目录名或时间冒充旧版固件身份。

只写一个 0600 的 `/tmp/lg6851f-download-state.XXXXXX` 报告，不读取短信正文/号码和无线口令；报告仍含客户端 MAC 与筛选后的规则信息。没有设置 UCI、sysctl、nft 或 TC，没有执行网络策略脚本、模组查询、服务停止、升级、切槽或重启。未访问实机。现有临时 DSCP 表保持不变，重启会消失；撤销命令为 `nft delete table inet lg6851f_dscp_test`，采集脚本不会自行撤销它。

此提交仅增加诊断工具及说明，不修改固件网络策略，不触发云编译。需要目标机报告后才能选择有依据、可回退的下一项热测试，不能提前宣称已定位剩余速度损失。
