# 下载速度与 500 Mbps 历史运行状态对照

## 基线口径

用户提供的[成功记录](https://chatgpt.com/share/6aff1a0f-83b8-83e8-b6d4-fc43ab1b1d0e)不是“固件默认关闭 QoS 就能达到 500 Mbps”。实际是旧版固件默认开启 QoS，用户在 SSH 排查并操作后达到该速度。

2026-11-12 的原始用户输出显示：固件为 b6c3ce7f60950cddfa75be0d0c591ffc2ae4cc7a（v1.0.15），执行 `/etc/init.d/lg6851f_fair_qos stop` 后，ccmni2 为 fq_codel，ifb-cellular 不存在，入口重定向为空；随后用户报告下载约 15 GB，速率 300～500 Mbps，大部分时间接近 500 Mbps，没有重启，未计时。此为一次实际运行结果，不代表全部内核故障已解决。

分享记录中可核实的操作链以用户贴回的命令和结果为准，不把助手建议当作已执行操作，也不排除记录外还存在手动修改。不能只对比 enabled 默认值，还必须核对启动时是否曾安装过 CAKE/IFB、停止后的规则、实际中断/RPS 和配置状态。

当前设备实际固件为 11dd25e3839e5da76b9c38d7bc674020f3d435d9（v1.0.20），源码仓库后续的说明及临时测试工具提交不等于用户已刷入新固件。

## 本轮用户已验证的状态

- 旧版临时 QoS 开启约 100～150 Mbps；关闭后约 10～20 Mbps，均为下载 Mbps、同一测速节点。
- 关闭结果 OFF_RC=0；ccmni2 实际 fq_codel、IFB 和重定向已经清理，不能继续把这个状态归因于残留 CAKE。
- 不开启 CAKE/IFB，仅增加临时 nft 表 lg6851f_dscp_test，在蜂窝下载转发路径清除 IPv4/IPv6 非 CS0 的 DSCP 后，恢复约 150～250 Mbps。IPv4 计数命中，IPv6 当时没有命中。这是独立于完整 QoS 的部分恢复线索，不是最终 500 Mbps 修复或内核稳定性结论。
- 测速手机确认是 5a:b8:72:03:17:2a，5 GHz、80 MHz、HE 双流，收发 PHY 1200.9 Mbps。不能拿另一个 390 Mbps 单流客户端解释其速度上限；PHY 速率本身也不保证实际吞吐。
- OpenClash 配置为 0，用户确认未开启。150～250 Mbps 时十秒 CPU 平均约 46.7%，最忙核平均约 53.8%；没有证明持续单核满载，也不能排除短时突发。
- 原厂系统用户报告约 440～500 Mbps；250 Mbps 不作为完成目标。累计 Wi-Fi 失败计数不是当前丢包率，蜂窝 RX 降低也不能单独排除下游 TCP 反馈导致的降速。

## 下一步：一次被动运行状态采集

新增 `scripts/lg6851f-collect-download-state.sh`，由用户在现有互联网测速/下载期间运行，不恢复已经停止的局域网测试。默认两次计数采样间隔 10 秒，可选 0 或 20 秒。命令和无线站点查询也有耗时，分析应使用报告内 `/proc/uptime` 的实际间隔，而非假定严格十秒。

采集包括：实际固件身份、主要安装包版本、网络配置白名单、TC 与 DSCP 状态、标准 GRO/RPS/IRQ、脚本与 ROM 指纹、服务 PID/运行状态、CPU/softnet/接口与站点累计计数。仅在核实已挂载 P46 的分区身份后读取最多 8 份旧 upper 网络配置白名单，不主动挂载，不把归档目录名或时间冒充旧版固件身份。

只写一个 0600 的 `/tmp/lg6851f-download-state.XXXXXX` 报告，不读取短信正文/号码和无线口令；报告仍含客户端 MAC 与筛选后的规则信息。没有设置 UCI、sysctl、nft 或 TC，没有执行网络策略脚本、模组查询、服务停止、升级、切槽或重启。未访问实机。现有临时 DSCP 表保持不变，重启会消失；撤销命令为 `nft delete table inet lg6851f_dscp_test`，采集脚本不会自行撤销它。

此提交仅增加诊断工具及说明，不修改固件网络策略，不触发云编译。需要目标机报告后才能选择有依据、可回退的下一项热测试，不能提前宣称已定位剩余速度损失。

当前环境检查：`sh -n` 与 `git diff --check` 通过；实际执行配置白名单函数，验证保留 APN/加密类型等诊断字段，排除口令、用户名、号码、IMSI 和 DNS，并拒绝配置符号链接。无效采样间隔及非 LG6851F 主机均在采集前拒绝。没有在目标 BusyBox 执行完整采集或进行新的下载压力测试。

## 实机报告 ffKpho 的结果

采样的两个 `/proc/uptime` 相差 11.01 秒。ccmni2 RX 增加 158,505,968 字节，平均 115.17 Mbps。5 GHz AP TX 增加 150,341,288 字节，平均 109.24 Mbps。测速手机站点计数的实际间隔为 10.866 秒，TX 增加 142,557,758 字节，平均 104.96 Mbps。第二台站点约 2.39 Mbps。接口和站点计数采样略有错位，统计口径不同，不能相减当作丢包率。

CPU 总忙碌比例约 35.5%，最忙核为 CPU1（41.2%）。四核 softnet 的 dropped 和 time_squeeze 均无增量，ccmni2 历史接收丢包计数 1054 也没有增长。测速手机 TX 失败计数增加 2014，需要继续观察无线重传；计数不能直接换算为 TCP 丢包率。这段数据没有显示 CPU 或接收队列持续饱和，也无法定位蜂窝入口低速是上游限制还是 TCP 对下游状况的反馈。

实际 QoS 关闭，ccmni2 使用 fq_codel，未出现 IFB/入口重定向。防火墙流量卸载关闭，OpenClash 未启用。临时 DSCP 表已累计匹配约 7.28 GB 的 IPv4 流量，IPv6 未命中。原报告没有在采样结束时读 DSCP 计数，累计值不可当成 11 秒内命中比例。当前 APN 为 3gnet，与已知 500 Mbps 记录一致。P46 唯一归档为 ctnet、QoS 关闭，没有证据将它认定为 500 Mbps 时使用的配置。

ccmni2 RPS 掩码为 `6`（CPU1、CPU2），以太网 RPS 为 `f`，与配置策略一致，ccmni_gro 模组参数为 1。Wi-Fi 的 mt7996e 和 mt7996e-hif 中断累计均在 CPU0，DPMAIF_AP、MED_RX_IRQ 与活跃 CCIF 也在 CPU0。`lg6851f-net-affinity` 按名称查找中断时用了 `/proc/irq/*/actions`，标准 Linux 名称字段位于 `/sys/kernel/irq/*/actions`。此缺陷在 v1.0.15 已存在，实机两份脚本指纹也与当时源码相符，追溯当前降速仍缺少旧版的实时 IRQ 数据。

Wi-Fi 显示为 MediaTek Gen3 PCIe MSI。Linux 6.18.44 中该控制器的底层 MSI irq_chip 没有 `irq_set_affinity`，其链式父中断来自板载 PCIe 控制器。设备树上的两个父硬件中断号为 GIC 320、310。应先确认实机是否暴露这两个父中断的 affinity 接口及每核计数，再决定能否做临时对照，不向 Wi-Fi 子 IRQ 或猜测的 Linux IRQ 写入掩码。

采集器版本 2 已改用 sysfs 读取 IRQ 名称，并从 `/proc/interrupts` 查找网络设备 IRQ。新增查找 PCIe 父 IRQ，以及在两次采样中保存中断和 DSCP 计数。接口信息改用目标 BusyBox 支持的 `ip link show`，其他计数仍用 sysfs。语法和差异检查通过，隔离回放验证了可见的 MSI 子 IRQ、未出现在 `/proc/interrupts` 的 GIC 父 IRQ 及缺失的 affinity 属性。此次未改变固件绑核策略。

## PCIe 父中断与发布镜像核对

实机 `r0-11dd25e` 的 `/sys/kernel/irq` 显示 GIC 320 对应 Linux IRQ 197，GIC 310 对应 IRQ 198。两者都缺少 `/proc/irq` 中的 `smp_affinity` 和 `effective_affinity` 文件。两个 Wi-Fi MSI 子 IRQ 208、209 的累计计数仍全部在 CPU0。当前固件没有可用于该 PCIe 父中断绑核对照的 `/proc` 接口，结束这条运行时测试分支。

下载两版公开 B 槽发布包，通过 GitHub 资产和包内 manifest 核对 SHA256。读取 `boot_b.img` 与 `rootfs_b.img`，并从 rootfs 核实固件编号分别为 b6c3ce7 与 11dd25e。[v1.0.15 发布包](https://github.com/adian2020/openwrt-mt6990-lg6851f/releases/tag/v1.0.15) · [v1.0.20 发布包](https://github.com/adian2020/openwrt-mt6990-lg6851f/releases/tag/v1.0.20)

- 两版 `/lib/modules/` 的 131 个文件及 `/lib/firmware/` 的 17 个条目均匹配，包含 mt76、mt7996e 和 CAKE。设备树 SHA256 同为 `9220c60bda43d3d8afae909deba7487840a19d446882a17717ebb06423df8ea6`。
- 解压的两份 ARM64 `Image` 均为 15,953,928 字节。逐字节比对的 130 个差异都位于构建主机名、编译器版本中的提交标识、构建时间（含十六进制时间戳）或 GNU build ID。CCMNI、DPMAIF 和 PCIe 所在内核的程序字节一致。
- `netifd`、`wpad`、`fw4`、`ql_datacall.sh`、APN 解析程序、`mipc_wan_cli`、`atcid`、`libnetagent.so`、`libmipc_msg.so` 和 `libqlril.so` 哈希一致。模组包有差异的文件集中在存储和 Wi-Fi 启动脚本、模式控制、状态查询和短信读取。QoS 脚本、新增短信池以及实机配置仍是两版可比较的差异。
