# MT6990调频驱动与设备树离线核对

## 范围与结论

用户在时钟摘要读取导致卡死重启后，要求继续检查驱动与设备树。本次仅离线读取源码，未连接实机、加载模块、读取硬件寄存器或启动云编译。源码基线为cloud-build的57c3bd5；另一LG6851F-Pro项目保持暂停，仅将已有驱动源码作为参考阅读。

当前设备树描述四个Cortex-A55核心，属于一个簇、一个共享频率域。当前内核配置启用了不匹配此设备的通用MediaTek调频驱动，却关闭了与该频率域节点匹配的硬件调频驱动。这解释了源码层面为什么不会由这两套驱动提供标准cpufreq policy接口，与用户实机节点不存在的结果一致。真实当前/最大MHz仍未接入，不能把此项写成已经修好。

## 设备树核对

实际镜像配置target/linux/mediatek/image/mt6990.mk指定mt6990-fiberhome-lg6851f设备树。target/linux/mediatek/dts/mt6990-fiberhome-lg6851f.dts中：

- cpus节点有cpu@0、cpu@001、cpu@002、cpu@003四个Cortex-A55核心；cpu-map仅有cluster0，包含core0至core3。
- 四个核心的performance-domains全部是<0x07 0x00>，共享同一控制器的第0个频率域；不能照参考图当成三个独立CPU簇。
- phandle 0x07对应performance-controller@0011bc00，compatible为mediatek,cpufreq-hw，实际reg起点0x11bc10、长度0x120。节点名称与reg存在偏移，以reg为准。
- clock-frequency为0x65633340，即1701000000 Hz（1701 MHz）。这是静态设备树属性，不能证明运行时频率或硬件最高频率。
- 唯一operating-points-v2引用指向mali GPU的OPP表，不是CPU表，不能借用其中数值作为CPU档位。
- 邻近还保留mediatek,mcupm-dvfsp及mediatek,cpufreq-hybrid厂商节点；仅有节点不意味着当前内核已实现相应固件协作。

## 配置与驱动匹配

使用仓库scripts/kconfig.pl按通用配置、MT6990子目标配置的顺序合并，结果为：

```text
CONFIG_CPU_FREQ=y
CONFIG_ARM_MEDIATEK_CPUFREQ=y
# CONFIG_ARM_MEDIATEK_CPUFREQ_HW is not set
CONFIG_CPU_FREQ_DEFAULT_GOV_USERSPACE=y
# CONFIG_CPU_FREQ_THERMAL is not set
```

ARM_MEDIATEK_CPUFREQ_HW的关闭项来自target/linux/generic/config-6.18第476行，MT6990配置没有覆盖它。该结果是当前源码配置合并检查，不声称已导出用户运行内核的最终.config。

对照Linux v6.18的drivers/cpufreq/mediatek-cpufreq.c及仓库现有840、841、843、844、350-21系列调频补丁：通用驱动在根节点机型表匹配，没有mediatek,mt6990，初始化会因不匹配返回ENODEV；这些本地补丁没有加入MT6990。因此打开CPU_FREQ和ARM_MEDIATEK_CPUFREQ本身并不足够。

上游drivers/cpufreq/mediatek-cpufreq-hw.c的匹配表包含mediatek,cpufreq-hw，基础寄存器布局与当前节点声明有对应关系，但需要进一步验证固件协议：

- 从硬件LUT读取频率档位；最大档位必须来自有效且完整的实机档位表，不能拿代码里的范围检查上限代替。
- 初始化向ENABLE偏移0x84写1，并轮询HW_STATE偏移0x8c；退出会写0，调频还会向PERF_STATE偏移0x88写索引。
- get接口读取请求索引，再查LUT得到频率，不等于直接测得物理PLL频率。
- 初始化检查硬件及SVS状态，涉及固件准备、散热限制和控制权交接。当前CPU_FREQ_THERMAL也未开启，需要一并审查，不能只打开硬件驱动选项就宣称安全可用。

## 已有适配参考

另一工作区的drivers/lg6851f_cpufreq_hw.c包含MT6990硬件LUT适配，限定机型、寄存器资源和所有CPU共享第0域，与当前设备树一致。它还实现档位校验、调频请求、散热限制以及直接读取PLL寄存器的可选属性。

该代码同样会写ENABLE和档位请求寄存器，还映射PLL与分频寄存器；并非单纯被动读取显示数据的模块。现有预编译ko即使内核版本字符串相同，也不能据此认定配置、符号ABI和固件状态兼容。本次未复制、编译、加载或执行这套实现，也未运行历史/dev/mem读取工具。代码中的2200000 kHz是合法范围检查上限，不是已经取得的硬件最高频率。

## 卡死事件与后续边界

clk_summary读取进入内核时钟驱动，可能访问多个时钟提供者。没有当次调用栈或复位记录，目前不能将卡死精确归因到某个寄存器、PLL或看门狗。停止此诊断入口，不再让用户重读，也不使用timeout重复尝试；当前看板采集没有该回退路径。

频率显示应按本机实际共享域设计成一组四核当前/最大MHz，而不是填三个相同的值伪装三个独立簇。此前三行只是界面结构，尚无实机频率，本次未擅自变更用户要求的界面，后续应按上述硬件结论调整。

下一步若实施调频接口，需要先审查MCUPM固件就绪与所有权、LUT有效性、初始化/卸载恢复和散热联动，再明确所显示的是请求档位还是物理频率。此次未启用驱动、改设备树、设定频率或安排实机探测；云编译继续等待用户明确启动。

## 继续核对与最终决定

用户随后要求继续寻找读取办法，并最终明确“既然没有就没必要添加上去了”。以下为补查结果，不把“尚无可直接接入的可靠接口”扩大为硬件永远无法实现：

- 找到SBA6D-OSS公开的MT6990厂商内核源集，固定提交c7508cb46a6f51c9873604d6a94c94d5c433a8b6。其mediatek-cpufreq-hw.c同样需要写ENABLE、档位请求和退出寄存器，没有提供可直接调用的独立只读用户态服务。
- 厂商cpufreq_v1/cpufreq-dbg.c的get_cur_phy_freq直接readl读取PLL和分频寄存器；phyclk proc接口只是其包装。初始化还依赖MCUPM IPI和固件共享内存，不能作为一个普通文本查询文件独立搬入当前内核。即便仅提取只读部分，仍需证明寄存器在当前电源状态下可访问；时钟摘要卡死事件后不再安排此类实机探测。
- 当前cpuhvfs的两组pll-con是0x2f4与0x330，时钟驱动分别定义为ARMPLL_LL_CON2和CCIPLL_CON2。后一项是互连时钟，不能再当成第二个CPU簇，更不能据此生成三簇CPU频率。
- 本地medmcu_dvfs.c管理SCP辅助处理器的DVFS，不是这四个Cortex-A55的频率来源。ql_powerd中可见的是USB/唤醒/休眠控制路径，未找到可用于本机CPU频率的查询入口。
- 合并配置关闭ARM_SCMI_PROTOCOL、ARM_SCPI_PROTOCOL与ARM64_AMU_EXTN，当前设备树也没有相应SCMI/SCPI协议节点。PMU计数与耗时最多提供特定采样窗口的估计，不是当前/最高档位表；不引入负载测试来凑显示数值。BogoMIPS、静态clock-frequency及宣传峰值同样不代替真实MHz。
