# 本机preloader重试累计与回退条件实证

后续适配：用户继续要求下一步处理，正常启动后单槽TRY确认已实现，详见《2026-11-15正常启动确认与单槽TRY清零修复》。本文保留前级分析时的证据与当时尚未加入自动确认的状态，不代表最新源码仍缺少该适配；实机效果仍未验证。

## 结论及边界

已定位本机实际计数写入、复位分类、回退阈值和主流程调用顺序。TRY不是读取Linux错误日志后生成的“启动失败次数”；字段虽叫tries_remaining，本机执行的是加1。某些软件/看门狗复位路径可累计，成功进入Linux不会自动让前级知道启动已完成。

自编译源码缺少原厂正常启动后清当前TRY的步骤，是已核实的适配差异。执行原始函数可以复现：Linux不清计数时，B仍可进入Linux并逐步留下TRY=1、2、3、4；下一轮引导检查切A，B的4保留；原厂A的S99随后具备恢复B的条件。

这与用户日志中多次B槽6.18正常联网、有序shutdown、最后A原厂启动且B变为5.4相容。但当次回退前的计数、硬件复位状态、RAM_CONSOLE及实际恢复QL_AB日志未保存，不能认定每次历史复位原因，或声称捕获了当次复制。内核偶发故障仍不能仅凭此排除。

## 计数递增与复位分类

以下均为该哈希对应前缀内的文件偏移，不能用于其他设备操作：

| 偏移 | 实际作用 |
| --- | --- |
| 0x10a4 | ql_increase_boot_retry_count：读BCAB，按优先级选槽，TRY加1写回 |
| 0x10de—0x10e6 | 读取TRY、加1、截断为8位并存回结构 |
| 0x44ad4 | 依据保存的WDT状态、缓存mode及PMIC查询分类，部分分支关闭递增标志 |
| 0x44920、0x44934 | 设置/读取ql_increase_ab_retry_flag，本镜像初始数据为1 |
| 0x142f6—0x14336 | 分类2且标志1时递增，随后生成boot.reason=4 |

递增函数选择优先级较高的槽，同优先级选A。它不检查panic、Wi-Fi、联网，也不以SUCCESS=1阻止递增。8位值255会回绕0，事后读到0不能证明从未发生复位。

0x44808先缓存WDT状态并清0x20010位；0x44ad4屏蔽0x2fc0ff00，结合缓存mode的0x2000位分类。合成状态0x40000000、mode含0x2000、PMIC特殊复位查询为假时，分类2、标志1、TRY加1、boot.reason=4；0x80000000在同条件也走此路径。mode不含0x2000时，这两个样本为分类1/reason=3，不在此路径递增。另有特殊状态/PMIC分支把标志清0，即使分类2/reason=4也不加。

因此该路径并非某个Linux报错的专属计数。**boot.reason=4既不等于内核崩溃，也不能单独证明这次一定加计数。** 有序shutdown之后也出现reason=4，不能据此改称启动失败；具体历史硬件复位原因仍需当时寄存器/前级日志。本轮未在实机读取MMIO或clk_summary。

## 切槽条件和先后顺序

原始检查函数0x1c04：先读优先后缀、其TRY/SUCCESS和当前eMMC硬件启动区。如果硬件区与后缀不一致且异常检查允许，切换到所选区；这可以是手动改优先级后的正常协调，不代表失败超限。

两者一致时：当前TRY<=3继续；当前TRY>3还要满足RAM_CONSOLE异常检查为否、另一槽TRY<=3，才把另一槽设为优先、设置硬件启动区并请求复位。两槽都>3打印don't switch boot，异常检查为真也跳过。SUCCESS在这个阈值路径只用于日志，不阻止回退；原厂Linux另外使用它决定复制，手动工具仍保留SUCCESS风险确认。

主流程的实际调用链：

```
0x9642 -> platform preinit 0x13c28 -> 0x13dc6调用A/B检查0x1c04
随后0x96f0 -> 复位原因函数0x13eac -> 特定WDT分支0x14326递增
```

**先检查已有TRY，再按本次复位原因递增。** 从B=0开始、每轮都符合递增条件、Linux不清计数的例子：

| 轮次 | 检查时B的TRY | 行为 |
| --- | --- | --- |
| 1 | 0 | 继续B，后续加到1 |
| 2 | 1 | 继续B，加到2 |
| 3 | 2 | 继续B，加到3 |
| 4 | 3 | 继续B，加到4；仍可进入B的Linux |
| 下一轮 | 4 | 另一槽<=3且异常检查允许时切A并复位，本轮B不再递增 |

不是“第4次重启必定当场切槽”。实际受起始值、复位类型、是否清零和异常检查影响；下一轮检查本身也不要求本次复位还会递增。RAM_CONSOLE的0x17090检查WDT记录、nonrst2及mboot的fiq_step/exp_type，未取得历史快照就不能认定当次一定通过。

## 原厂恢复与适配差异

原厂zmtk_boot_done源码及前轮实际函数回放已经确认：正常启动清当前TRY；另一槽TRY>3时，ab_image_sync从当前槽复制16个对应分区（含boot/rootfs），之后清另一槽TRY。前级切槽与Linux复制恢复是不同阶段。

这能够解释为何用户明确写boot_b/rootfs_b并曾运行6.18，事后B却成为5.4；当前A/B均0也不能否定此前累计。但本次没有实际复制时刻日志，不把机制能力说成已捕获的历史动作。

正确修复方向是在**真实完成启动后，仅清当前槽TRY一次**：核对实际bootslot/root、合法BCAB和新鲜快照，保存共享P46证据并读回。不能启动早期或周期盲清，不能强写SUCCESS、改另一槽、提高阈值或禁用保护。这个自动运行时写入尚未加入，不能宣称误回退已修复。

手动功能已在源码提供“系统 → 启动槽位”及/usr/sbin/lg6851f-slotctl：备份/确认后只改优先级和目标TRY，保留原厂前级协调硬件启动区。实际设备切槽仍待验收，旧固件不会因推送自动增加页面。

## 离线复现和验证

宿主脚本scripts/analysis/replay_lg6851f_preloader.py只接受上述前缀哈希，使用Python Unicorn执行原始Thumb函数。BCAB存储、PMIC、eMMC启动区设置和复位请求使用内存夹具；不操作真实设备。夹具边界的函数入口执行BX LR，保留Thumb条件状态，双向分支都检查。RAM_CONSOLE既做可控返回值组合，也单独执行实际函数；组合引导示例执行其正常记录分支。

```
python3 scripts/analysis/replay_lg6851f_preloader.py /path/to/mmcblk0boot0.prefix.img
```

共420组通过：计数86（含失败返回及对应1字节范围）、复位分类/路由32、双向硬件启动区/阈值/异常/SUCCESS组合288、RAM_CONSOLE实际函数8、按原始调用顺序排列的引导阶段6。组合保留B=4，切A后A进入Linux前为A=1/B=4，供对照S99条件。

这不是整机上电、真实存储/验签/复位或Linux复制验证。研究脚本语法及diff检查通过。本轮仅新增宿主分析与说明，没有改运行时计数、阈值、SUCCESS、内核保护、签名或A/B打包，没有启动云编译或自动监控。
