# MU300开机逻辑对照与提速候选

## 核对范围

用户提供adian2020/mu300-linux的minikano-openwrt-feats分支，并报告该仓库固件首次开机约38秒出现WiFi且可上网。本次固定核对远端提交b35932ab3c7c7f1df3e1ad6a74056835bef13867，对照本仓库cloud-build的f2c1a72。只做源码分析，没有改动启动逻辑、重启实机、触发云编译或恢复监控。

本地mu300-reference并非该远端分支头。本次逐一核对109个启动候选文件的Git blob：108个一致，唯一不同的mu300-usb已另行从远端固定提交读取；没有直接把本地旧提交冒充用户指定分支。

38秒是用户报告，不是本次复测。不同芯片、引导器、内核、无线固件和蜂窝注册时间不能直接换算；不能承诺LG6851F也能达到38秒。CPU频率功能已经按用户决定取消，本次不重新启用。

## MU300的实际启动链

1. boot/init准备根文件系统、存储和必要模块，按真实分区就绪提前结束等待，随后switch_root。它还在后台预读模块文件，保留正常procd加载流程；这不是跳过模块初始化。
2. S09mu300-vendor尽早通过procd启动NV服务cp_diskserver和modem_control，让CP启动时间与后续系统初始化重叠。设备节点缺失时在自己的服务进程中等待，不串行挡住整个rc启动链。START必须写09；源码记录S9字典序排到S19之后曾造成额外延迟。
3. S12mu300-hw将主体硬件准备放到后台，依次准备监管数据库、SC2355/WCN驱动和无线配置。监管域与实际PHY就绪后启动AP；已有相同配置且hostapd已ENABLED时直接保留，不重复down/up。
4. S19mu300-atd在S20network之前建立持久命令通道所有者。radio-warmup在后台等待真实命令通道，不依赖一个固定长sleep，也不在每次查询时另开竞争读取者。
5. S20network通过mu300cell协议调用mobile-data拨号。射频准备先等待已有URC，注册等待以事件触发查询为主、低频查询为辅，避免状态查询排挤初始化。拨号、信号查询保持既有通道分工，不能把这些展锐通道名直接搬到MT6990。
6. 后台bootmark和boot-milestones记录内核uptime及地址、路由、DNS就绪；结果探针不发AT命令。源码记录早期AT轮询探针曾制造约43秒假延迟，说明测量本身也必须让行拨号。

## 仓库中有实测记录的提速

docs/U30AIR-WIFI-BOOT-20261023.zh-CN.md记录：该设备旧regdb-load在没有firmware sysfs helper的内核上，仍等待永远不会出现的请求节点，监管数据库准备用了20.35秒。修正条件后该阶段0.35秒，热点AP-ENABLED从约41秒提前到21秒；蜂窝地址约27.74秒就绪。它保留签名验证、国家码与恢复路径。

另一份U30AIR-FULL-BACKPORT-LIVE-20261023.zh-CN.md记录内核uptime下地址37.33秒到27.69秒；电脑侧reboot到SSH为42.33秒到35.14秒。这些起点不同，均不是本次LG6851F的实机证据，也不能与用户从开关机/刷机开始计时的38秒或78秒直接相减。

本机没有使用MU300的regdb-load脚本，不能套用“改一处就减20秒”。本机源码配置启用了firmware user-helper fallback，五个MT6990专用无线固件/EEPROM也都存在于板级base-files；不能仅因CONFIG_PACKAGE_kmod-mt7990-firmware未选中就判定缺固件。是否发生某次固件请求超时，必须看当次启动记录。

## 与LG6851F现状对照

| 做法 | 当前LG6851F | 可借鉴程度 |
| --- | --- | --- |
| WiFi与蜂窝注册并行 | 已实现。S21助手只等待PHY和配置；首次不等蜂窝，后续交netifd | 保留已有修复，不再重复增加另一套助手 |
| 不重复启动可用AP | 已实现。已配置的WiFi不再由首次助手反复拉起 | 继续保留用户开关，不照抄MU300的down/up |
| 存储/NV/CP尽早启动且只启动一次 | S09存储、S10 NVRAM、S11 FSD、S12 MD init；S19不再重复拉起 | 原则已具备，不新增第二个MD启动者 |
| 拨号所需控制服务在netifd前准备 | wait_modem_stack_ready要求scd(S53)、ql_netd/RIL(S85)、atcid(S96)等进程，条件满足后才开射频 | 是候选。需确认厂商依赖后再安排关键服务，不能把START数字当秒数或直接改成09 |
| 开机查询统一给拨号让行 | MIPC状态查询在接口未up时退出；高级参数等接口up后采集 | AT身份、CESQ、注册查询尚未统一按up让行，存在竞争窗口；不是已证明造成当前延迟 |
| WiFi准备不受整个系统启动链拖累 | 标准S10boot同步执行kmodloader及首次uci-defaults；S21助手在它之后才启动 | 优先定位模块加载、首次配置耗时；不能把整个S10boot直接后台化 |
| 用结果与阶段时间线定位，而不靠固定sleep猜 | 已有P46持久内核/系统日志、WiFi uptime标记及只读采集脚本 | 值得补齐preinit、存储、模块、PHY、AP-ENABLED、接口up阶段对应关系 |

## 后续优先顺序与限制

第一优先应分清“什么时候PHY出现”和“什么时候hostapd真正AP-ENABLED”。本机首次助手已经不等待蜂窝，继续删拨号等待不一定提前WiFi；如果主要时间在S10模块初始化或更早的引导器/内核，调整S21助手优先级解决不了。

第二优先核对关键控制服务启动依赖，争取让CP、控制通道、无线准备重叠。保留NVRAM挂载、厂商独占通道和CCCI就绪检查；不照抄展锐的SFUN、SMMSWAP、SIPC、CP loader、双卡或Android chroot。

第三优先统一开机信息采集让行。当前状态脚本的query()保护了MIPC调用，但at_query()尚未检查接口up，且调用发生在身份与详细信号分支。应评估在首次联网前暂停非必要AT采集，用户手动关闭射频时也不能靠状态采集重新开射频。此项是源码发现的可优化点，本次未修改，不能算实机效果已验证。

本机6秒CMIPC关闭冷却不是MU300那种已确认无效等待，不能删；首次/升级overlay清理、CONN_RO校验修复、恢复模式和A/B签名边界也保留。GNSS修复在真正修复后可能执行一次重启；需用对应记录区分它与正常开机，不能为缩短时间跳过校验或刷分区。

用户之前的boot-timing报告只保留开机约40分钟后的片段，缺少当前成功固件从上电到AP-ENABLED的完整阶段。本次因此只给出候选和证据，不指定未经测量的节省秒数，也未更改运行代码。
