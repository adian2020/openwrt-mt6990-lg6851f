## 开机无网与射频修复链

新面板继续使用 luci.modem5g → MT6990 原拨号链路，不安装展锐后台。
开机仍由 netifd 的 ql_datacall_setup 负责：先等原厂进程和 MD 就绪，
再确认射频开启，之后才进行 SIM/APN 与数据连接。没有新增抢占控制口的启动服务。

- 新建配置明确设 radio_enabled=1、auto=1。原有用户配置的射频关闭与 autostart=0
  予以保留；保留配置升级时不重写已有 APN、IP 类型、MTU 或 SIM 自动配置选择。
- 查询成功且状态明确为 OFF 时才发送开启命令，并读回确认；忙、超时、未知或失败
  查询不当作 OFF。重试有界，临时失败返回待重试，不设置永久阻断标志。
- 在控制锁内再次检查用户射频策略，避免等待期间的显式关闭被开机流程撤销。
- 新旧页面统一调用 lg6851f-radio-control：控制锁覆盖设置、关闭冷却、读回及偏好保存。
  确认 ON 后保存并请求 ifup；确认 OFF 后保存并 ifdown；失败不伪报成功。
- 手动开关与锁频/自动恢复互斥；恢复监护检查显式关闭偏好，不自行重新开启射频。
- 网络存在未提交修改时不提交整个 network 配置，避免射频按钮顺带保存其他表单。
  两个页面均采用足够的 RPC 等待时间，拨号页也防止重复点击和忽略失败返回码。
- 拨号页定时读取接口与已有缓存，避免 ifup 返回后一直停留在旧的离线卡片；
  这不增加厂商查询，刷新时保留已展开的工程信息。

## 本机标称频段与模组上报分开

按用户给出的本机规格整理：

- NR：n1、n3、n5、n7、n8、n20、n28、n38、n40、n41、n75、n76、n77、n78。
- LTE FDD/补充下行：B1、B3、B5、B7、B8、B20、B28、B32（B32 为补充下行）。
- LTE TDD：B38、B40、B41、B42、B43。

实机模组能力掩码还包含 B46。这是模组上报，不据此宣称整机射频支持；
B46 只读展示，不开放本机手动选频。n76 保留在能力列表，但厂商工具拒绝输入 76，
因此同样暂不开放手动设置。“恢复默认”仍按模组完整能力回读校验，不删改原始掩码。
小区锁定的 UI、RPC 与 shell 同时校验频段及 PCI（LTE 0–503、NR 0–1007），保留 PCI=0。

## QCI、SA/NSA 与编码进度

- CQI 已实机读回 11；它是信道质量指标，不是 QoS 等级。
- QCI 不是确认不可读取。当前 ql_netd 有 data_call_get_qos_info/5gqos_info 与 QCI 日志，
  libqlnet 的 ql_data_call_get_qos_info 也确实存在；须按活动 CID 确认返回，而非套固定值。
  已请求现有 QoS 日志、ubus schema 和注册状态的只读采样。
- 已收到该采样：5GS 注册、EPS 未注册，结合 NR 连接支持采样时为 SA；QoS 日志为空，
  ubus schema 为通用二进制封装。已核对只读 getter 8/12/13，并提供无需新固件的
  采集脚本。随后实机 get_list 成功返回 580 字节空列表，SDK 未列出原生 MIPC
  上网连接；未继续查询其他上下文或填写等级。见 [注册与 QoS 采集](MT6990实机注册与QoS只读采集.md)。
- 已离线核对 sample_nw 第 7 项只调用 ql_nw_get_data_reg_status，并打印当前
  radio_tech/reg_state。该二进制映射明确区分 NR5G（18）和 NSA5G（19）。
  主动参数查询加入第 7 项，仅在读取成功、3GPP 域且注册有效时判别 SA/NSA；
  错误、未注册、未知结果保持未获取。第 7 项已实机读回 NR5G/FULL，确认当时为 SA；
  NSA 仍待实机样本，完整新固件看板尚未刷入验收。
- 这与 mipc_wan_cli 的十六进制 RAT 位图不是同一种枚举，不交叉套编号。
- 调制=1、MIMO=2 已读到真实数值，缺的是本固件 SDK 编码定义。暂不借其他机型
  的枚举强行显示 QPSK 或 2×2；原始数值继续可见。
