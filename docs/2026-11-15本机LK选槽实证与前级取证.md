# 本机LK选槽实证与前级取证

## 证据身份

用户上传 `lg6851f-bootchain.lbLeOn.tar.gz`，SHA256：

```
5e904a3e5091438e704954519ff739b5d0ecf36f4da26cf2f2472ba645ea8606
```

采集版本3，退出码0，阶段complete，lk_a/lk_b各1048576字节，两者内容相同。镜像SHA256均为：

```
5ce5ff892ca7dc2d443647dd27e05d3b4067743029f2603d6b2331b9d3a5091d
```

对应sysfs名称lk_a=p23、lk_b=p36，各2048扇区。采集时为原厂A槽5.4.238；控制快照仍为A优先级15、B优先级14，两槽TRY=0、SUCCESS=1。这个当前快照不能还原回退之前的TRY。

原始镜像不提交到公开仓库。下文偏移是该哈希对应文件内的偏移，不适用于其他版本或作为写入地址。

## 已验证的实际选槽函数

镜像有MTK头及多个子镜像：普通lk载荷在文件0x200、长度0x56ae4，虚拟基址0xda200000；aee_lk载荷在0x57da0、长度0x74780，虚拟基址0xdc600000。通过ARM启动向量、Thumb反汇编、PC相对字符串引用及调用点定位，普通get_suffix入口为0xa410，异常处理版本入口为0x668d0。

普通函数关键指令：

| 文件偏移 | 实际行为 |
| --- | --- |
| 0xa418 | 调用read_write_partition_info，传mode=0，即读取 |
| 0xa422—0xa42e | 比较BCAB magic |
| 0xa44c、0xa450 | 从读取结构的+12、+17取得两槽优先级 |
| 0xa456—0xa45c | 无符号比较：A<B时返回_b，否则返回_a |

普通boot加载路径0x18f40也调用此函数后拼接boot分区名；0xa8ae后的处理使用同一函数生成bootslot及对应root参数。因此它是实际启动路径使用的选槽函数，不是只看到fastboot菜单字符串。它本身只请求读取，不递增TRY、不写SUCCESS、不检查某个Linux panic错误码。

在已取得合法控制记录的条件下，其核心选择等价于：

```
suffix = priority_a < priority_b ? "_b" : "_a";
```

两个优先级相等时该函数选A；即使都为0，该函数局部仍返回A。这个局部结果不保证其他启动阶段允许继续。手动工具继续拒绝异常布局和记录，不借此放宽安全检查。

## 离线执行验证及边界

新增研究脚本 `scripts/analysis/replay_lg6851f_lk_selection.py`，只接受上述完整镜像哈希。使用宿主Unicorn执行原始Thumb函数，分区读取和日志输出在边界替换为内存夹具。没有运行或写入任何设备。

每个子镜像验证603组，共1206组：6组优先级组合；A/B重试分别取0、1、3、4、255；SUCCESS分别取0、1。600组正常读取场景中，两槽TRY与SUCCESS的变化不影响这个函数的选择。另3组覆盖get_suffix内部的读取失败/非法magic返回空后缀分支。

**范围限制**：读取辅助函数、真实存储、验签、复位处理、preloader和Linux服务都没有在这个回放中执行。尤其真实读取辅助函数还带有非法记录初始化逻辑，夹具中的非法magic分支不能外推成整机最终如何启动。此结果不能证明所有上游阶段都忽略重试计数，也不是整条引导链的硬件验证。

复现需要宿主Python的unicorn模块，不在路由器安装或运行：

```sh
python3 scripts/analysis/replay_lg6851f_lk_selection.py /path/to/lk_a.img
```

## 目前不能下定论的部分

镜像中确有bootctrl_switch_slot、switch_slot case a1/a2/b1/b2等字符串；仅有字符串不能证明这些分支在当前引导链执行，也不能据此填写计数递增规则。本次已验证的两个get_suffix不包含TRY递增或>3切槽判断。TRY由哪一级、在验签/载入之前还是之后更新，尚未定位到可验证的执行路径。

上一轮“正常自编译启动未清当前TRY，重试累计后切槽”的解释仍是重点假设，而不是已经证实的完整根因。现有日志中有正常联网和有序shutdown，也没有保存到此次回退对应的panic；不能把所有重启都说成内核启动失败。boot.reason=4同样不是已确认的错误分类。

已经独立确认的是原厂Linux的zmtk_boot_done：正常启动清当前TRY，另一槽TRY>3时从当前槽复制16个对应分区。此步骤可能解释用户曾写入并成功运行6.18的B槽后来变成5.4，但缺少实际复制时刻的QL_AB日志，不能声称该历史过程已完整捕获。

需要继续核对更早的preloader及可能的串口日志。上传的原厂bootctrl.sh明确把preloader_a/b映射到/dev/mmcblk0boot0、/dev/mmcblk0boot1；它们不是lk_a/lk_b，也不是普通GPT中的boot_a/boot_b。

## 下一步有界只读采集

采集脚本版本4增加显式参数 `--preloader`。默认不带参数仍只采LK；新模式不重复读取LK。

```sh
sh /tmp/lg6851f-probe-bootloader.sh --preloader
```

新模式先核实固定misc、boot/rootfs双槽和共享P46的PARTNAME、大小及分区号，再核对mmcblk0boot0/boot1的设备类型、名称、设备号和大小。每个启动区最多读前2048扇区，即1MiB，小于1MiB的区域只读实际长度；分区超过8MiB边界或身份不符则拒绝。使用既有12秒子进程看护，失败保留阶段及.partial证据。

输出 `mmcblk0boot0.prefix.img`、`mmcblk0boot1.prefix.img` 及哈希、现有启动控制字节、内核日志，包名仍为 `/tmp/lg6851f-bootchain.XXXXXX.tar.gz`。status.txt明确标识前缀范围，不能作为完整分区备份用于刷写。若前缀没有覆盖所需代码，再据其头部定位，不盲目扩大读取。

不写force_ro、不改启动区选择、不写misc，不访问整盘/RPMB/NV，不挂载分区，不复制固件，不清日志，不切槽或重启。用户提供采集包后再继续定位计数写入与阈值分支。

新增4项采集回归：显式模式且仅限两个前缀/保持源与写保护不变、错误布局或设备号拒绝、超限/缺失拒绝、未知参数拒绝；原有7项采集回归一并通过。研究脚本1206组回放通过。本轮没有改固件运行逻辑、自动清计数或强制成功标记，手动选槽功能维持已提交实现，不开启云编译。
