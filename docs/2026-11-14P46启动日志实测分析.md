# P46启动日志实测分析

## 输入与口径

用户提供 `lg6851f-boot-dashboard.txt`，1009行、84701字节，SHA256：`5c5ef32bc57e74b4dc47eb1e4903e6a3cb039652416417c9e4491326fb953684`。采集器版本4，当前固件源码45e730b，当前启动UUID前缀69ff2719，采集时内核uptime8290.33秒。

当前内核环形日志仅覆盖7381.320370至8284.093988秒，早期无线事件已不在其中；P46持久日志保存了两个独立启动区段。前段UUID前缀1b2ff2fa，首次WiFi助手执行自动配置；后段69ff2719与本次启动匹配，助手确认已经配置并交由netifd启动。前段没有单独保存rootfs源码SHA，因此将其称为较早的首次WiFi配置路径记录，不把它冒称严格控制变量的同固件首刷对照。

所有时刻均以内核启动为零点；不包含BootROM、preloader、LK、刷写、额外重启、手机扫描或关联耗时。两次启动分别计算，绝不跨UUID相减。

## 热点时间换算与校时

原始AP-ENABLED仅带系统实时时钟；同一早期区段中的内核消息同时带epoch与内核uptime。对每次启动分别取AP事件附近、uptime小于60秒的4个双时间戳内核消息，计算epoch减uptime的中位数，再换算同区段AP事件。

较早区段4个偏移范围1794616674.997613—1794616675.001923秒，本次1794648024.990902—1794648024.993267秒。相邻校准点相差数毫秒，支持把结果列为约值；系统日志时间与内核消息采集存在调度误差，不声称精确到毫秒。

本次后续日志存在显著系统时钟跳变。例如uptime87.017秒对应的系统时间已进入另一段epoch偏移，不能混用该偏移换算早期AP事件，也不能直接用墙钟日期计算开机或拨号耗时。本报告没有把较晚的modem5g up日志换算成确定的首次联网秒数。

## 可以确认与不能确认的结论

1. 两段记录中，常规模块批量加载约1秒，mt7996e模块initcall约0.44—0.45秒；没有观察到这两段驱动加载阻塞几十秒的证据。这不是对所有启动、异步驱动工作或网络压力稳定性的证明。
2. 较早启动在模块完成到WiFi助手之间有11.28秒，本次2.93秒，相差8.35秒。该区间包括uci-defaults、其他服务、调度及启动链工作，不能将整段直接命名为首次配置耗时。
3. 内核开始preinit到procd early之间，较早启动19.16秒、本次6.91秒；本次ubus到init之间又有7.37秒。它们是后续优先细分的位置，现有过滤日志未给出区间内部每个操作的起止，不能直接判定某个驱动或配置脚本是根因。
4. 精确的PHY首次注册时刻仍缺失。WiFi助手在35.17秒确认PHY已就绪只是上界，不能当作PHY刚出现；模块initcall返回也不能直接替代PHY目录创建时刻。两个AP均使用phy0（phy0.0-ap0和phy0.1-ap0），不能把radio0/radio1误称为两个不同PHY。
5. 本次首个热点约24.65秒、第二个约26.17秒，是内核计时下的成功AP事件；这不等于已将用户上电秒表的78秒缩短，也不能直接与MU300报告的38秒做等口径对比。
6. 日志有“eeprom load fail, use default bin”，但随后模块成功返回0、两个AP进入ENABLED。现有记录不支持将此提示判定为驱动启动失败或长延迟根因；本轮不隐藏提示、不跳过原有EEPROM校验。

## 后续测量

42e2a32已补齐下一版的preinit、S09存储/EEPROM、S10批量模块、逐个uci-defaults及后台PHY/AP观察打点。本次实测说明这些打点有必要，尤其要区分preinit/overlay准备、ubus建立至init以及默认脚本与其他启动工作。

本轮仅分析上传的日志并保存结论，不改启动顺序、驱动、超时、校准数据、槽位控制或软件源；不执行实机操作，不触发云编译和监控。无需为了当前已经取得的P46证据立即重启。
